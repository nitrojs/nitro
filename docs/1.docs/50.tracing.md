> See where each request spends its time, in the browser with the `Server-Timing` header and in observability tools with tracing channels.

Nitro measures its own work in two ways:

- [**Server timing**](#server-timing) adds a `Server-Timing` response header with a short summary of each request: time spent on KV storage, the database, the cache, and in total. Browsers show it in their devtools. It is enabled by default in development.
- [**Tracing channels**](#tracing-channels) publish one event per operation (route handler, middleware, storage operation, database query, …) on [`node:diagnostics_channel`](https://nodejs.org/api/diagnostics_channel.html). Nitro can log them as a timeline, send them to Vercel or Cloudflare tracing, and APM tools can subscribe to them. They are opt-in.

Both are built on the same instrumentation: server timing reads the `unstorage` and `db0` tracing channels to measure `kv` and `db`.

## Server timing

The [`Server-Timing`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing) header carries backend metrics to the client. Browsers show them in the devtools **Network** panel (under the **Timing** tab of a request) and expose them to JavaScript as [`PerformanceServerTiming`](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceServerTiming) entries.

In development, Nitro adds this header to every response, with metrics for its built-in KV storage, database and cache layers. In production, it is [opt-in](#enabling-server-timing-in-production).

```http
Server-Timing: kv;desc="3 ops";dur=1.2, db;desc="2 queries";dur=4.1, cache;desc="hit";dur=0.4, total;dur=12.3
```

The header covers every request handled by Nitro, including filesystem routes, errors, the [server entry](/docs/server-entry) and the [renderer](/docs/renderer).

### Metrics

| Metric | Description |
| ------ | ----------- |
| `total` | Time spent inside Nitro until the response headers are ready. For streamed responses, it does not include the time spent streaming the body. |
| `kv` | Time spent waiting on [KV storage](/docs/storage) operations made with `useKV()`. The description holds the number of operations. |
| `db` | Time spent waiting on [database](/docs/database) queries made with `useDatabase()`. The description holds the number of queries. Requires `experimental.database`. |
| `cache` | Time spent in [cached handlers](/docs/cache#cached-handlers), including cache route rules. The description holds the cache status: `hit`, `miss`, `stale`, `revalidated` or `bypass` (the request skipped the cache, e.g. with `shouldBypassCache`). |

A metric is only included when the request used it. Descriptions never contain storage keys, SQL queries or driver names.

### How durations are measured

Each `dur` is the wall-clock time during which at least one operation of that kind was in progress. Parallel operations count once:

```ts [routes/profile.ts]
import { defineHandler } from "nitro";
import { useDatabase } from "nitro/database";

export default defineHandler(async () => {
  const db = useDatabase();
  // Two 50ms queries in parallel: db;desc="2 queries";dur=50
  const [user, posts] = await Promise.all([
    db.sql`SELECT * FROM users WHERE id = 1`,
    db.sql`SELECT * FROM posts WHERE author = 1`,
  ]);
  return { user: user.rows?.[0], posts: posts.rows };
});
```

The same two queries run one after the other report `dur=100`. As a result, `kv`, `db` and `cache` durations never exceed `total`, and you can read them as "how long this request waited on X".

::note
Metrics can overlap. A cached handler that misses includes the time spent running the handler, and with the [`kv` cache driver](/docs/cache#kv-storage), cache reads and writes also count as `kv` operations.
::

### Runtime support

`total` and `cache` work on every runtime.

`kv` and `db` need the `node:async_hooks` and `node:diagnostics_channel` modules to attribute operations to the current request. They are available on Node.js, Bun, Deno and Cloudflare Workers (with `nodejs_compat`). On other runtimes, these metrics are left out.

### Adding your own metrics

Nitro does not need its own API for custom metrics: entries you add with your framework are merged with Nitro's.

In Nitro routes, use the `setServerTiming()` and `withServerTiming()` utilities from H3:

```ts [routes/report.ts]
import { defineHandler } from "nitro";
import { setServerTiming, withServerTiming } from "nitro/h3";

export default defineHandler(async (event) => {
  const data = await withServerTiming(event, "fetch", () => fetchReport());
  setServerTiming(event, "render", { dur: 3.2, desc: "Render" });
  return data;
});
```

In a [server entry](/docs/server-entry) built with another framework, use its own tools, such as [`hono/timing`](https://hono.dev/docs/middleware/builtin/timing) or [`@elysiajs/server-timing`](https://elysiajs.com/plugins/server-timing), or set the header on the response yourself:

```ts [server.ts]
export default {
  async fetch(req: Request) {
    const start = performance.now();
    const body = await render(req);
    return new Response(body, {
      headers: { "server-timing": `render;dur=${performance.now() - start}` },
    });
  },
};
```

Nitro keeps these entries and appends its own after them:

```http
Server-Timing: render;dur=8.4, total;dur=9.1
```

### Cross-origin requests

Browsers only expose `Server-Timing` metrics to scripts from the same origin. To make them visible to other origins, add a [`Timing-Allow-Origin`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Timing-Allow-Origin) header with a route rule:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  routeRules: {
    "/api/**": { headers: { "timing-allow-origin": "https://example.com" } },
  },
});
```

### Enabling server timing in production

Server timing is enabled by default in development only. To also send the header from production builds, enable the [`serverTiming`](/config#servertiming) option:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  serverTiming: true,
});
```

::warning
The header is visible to every client. The metrics are generic and never include keys or queries, but they still reveal how long requests spend on storage, the database and the cache.
::

::note
Server timing adds a small cost to every request: `kv` and `db` track each request in an async context (Nitro reuses its own when [`experimental.asyncContext`](/config#asynccontext) is enabled). Responses whose headers can't be modified, such as `Response.redirect()`, are copied to add the header.
::

To choose which metrics are reported, pass an object instead. Only the metrics set to `true` are enabled, in both development and production:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  serverTiming: {
    total: true,
    cache: true,
  },
});
```

To disable the header in development too, set `serverTiming: false`.

## Tracing channels

**🧪 Experimental!**

With the [`tracingChannel`](/config#tracingchannel) option, Nitro instruments its request lifecycle with [`TracingChannel`](https://nodejs.org/api/diagnostics_channel.html#class-tracingchannel)s. Each operation publishes `start`, `end`, `asyncStart`, `asyncEnd` and `error` events, which subscribers turn into spans. No OpenTelemetry SDK is needed.

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  tracingChannel: true,
});
```

Pass an object to only trace some producers, for example `{ h3: true, unstorage: true }`.

### Traced channels

| Option | Channel | Published for |
| ------ | ------- | ------------- |
| `srvx` | `srvx.request`, `srvx.middleware` | The whole request (with its response status) and each srvx middleware, on the Node.js, Bun and Deno server presets and in development |
| `h3` | `h3.request` | Each matched route handler and middleware |
| `unstorage` | `unstorage.<operation>` | Each [KV storage](/docs/storage) operation (`getItem`, `setItem`, …) made with `useKV()` |
| `db0` | `db0.query` | Each [database](/docs/database) query made with `useDatabase()`. Requires `experimental.database`. |

Tracing channels need `node:diagnostics_channel`, available on Node.js, Bun, Deno and Cloudflare Workers (with `nodejs_compat`), and in development.

::note
Spans that Nitro reports never include storage values or SQL queries. Database spans hold the query method (`sql`, `exec`, …) and the SQL dialect, since a query passed to `exec()` can contain user data.
::

### Logging a timeline

Enable [`experimental.tracingLogger`](/config#tracinglogger) to log each request's spans to the console as a timeline:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  tracingChannel: true,
  experimental: {
    tracingLogger: true,
  },
});
```

### Platform tracing

With `tracingChannel` enabled, these presets report spans to their platform's tracing:

- **Vercel**: spans are exported to the Vercel runtime as OpenTelemetry spans, next to Vercel's own [observability](https://vercel.com/docs/observability) data.
- **Cloudflare**: spans are reported as [custom spans](https://developers.cloudflare.com/workers/observability/traces/custom-spans/). Tracing must be [enabled on the Worker](/deploy/providers/cloudflare#tracing).

### Custom subscribers

APM tools and your own code can subscribe to the same channels. For example, a [plugin](/docs/plugins) that logs slow database queries:

```ts [plugins/slow-queries.ts]
import { tracingChannel } from "node:diagnostics_channel";
import { definePlugin } from "nitro";

const queries = tracingChannel<{ method: string; dialect: string }>("db0.query");
const starts = new WeakMap<object, number>();

export default definePlugin(() => {
  queries.subscribe({
    start: (message) => starts.set(message, performance.now()),
    asyncEnd: (message) => {
      const duration = performance.now() - (starts.get(message) ?? 0);
      if (duration > 100) {
        console.warn(`Slow ${message.dialect} query (${message.method}): ${duration.toFixed(1)}ms`);
      }
    },
  });
});
```

::tip
Keep a reference to the channel (here in the module scope) instead of subscribing by name with `subscribe("tracing:db0.query:start", ...)`: Bun drops those subscriptions when the channel is garbage collected.
::

# Tasks

> Nitro tasks allow one-off operations at runtime: named server-side actions such as database migrations, cache cleanup, or content syncing that you can run on demand, on a schedule, or from the CLI.

## Opt-in to the experimental feature

::important
Tasks support is currently experimental.
See [nitrojs/nitro#1974](https://github.com/nitrojs/nitro/issues/1974) for the relevant discussion.
::

In order to use the tasks API you need to enable the experimental feature flag. Tasks are scanned from your [`serverDir`](/docs/configuration), which has to be set as well:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  serverDir: "./server",
  experimental: {
    tasks: true
  }
})
```

All examples on this page assume this config.

## Define tasks

Tasks can be defined in `tasks/[name].ts` files inside your [`serverDir`](/docs/configuration).

::note
Like routes and plugins, tasks are only scanned when [`serverDir`](/docs/configuration) (or `scanDirs`) is set; no directories are scanned by default.
::

Nested directories are supported. The task name will be joined with `:`.

```txt
server/
  tasks/
    cleanup.ts       <-- cleanup
    db/
      migrate.ts     <-- db:migrate
nitro.config.ts
```

**Example:**

```ts [server/tasks/db/migrate.ts]
import { defineTask } from "nitro/task";

export default defineTask({
  meta: {
    name: "db:migrate",
    description: "Run database migrations",
  },
  run({ payload, context }) {
    console.log("Running DB migration task...");
    return { result: "Success" };
  },
});
```

### Task interface

The `defineTask` helper accepts an object with the following properties:

- **`meta`** (optional): An object with optional `name` and `description` string fields used for display in the dev server and CLI.
- **`run`** (required): A function that receives a [`TaskEvent`](#taskevent) and returns (or resolves to) an object with an optional `result` property.

```ts
interface Task<RT = unknown> {
  meta?: { name?: string; description?: string };
  run(event: TaskEvent): { result?: RT } | Promise<{ result?: RT }>;
}
```

### `TaskEvent`

The `run` function receives a `TaskEvent` object with the following properties:

- **`name`**: The name of the task being executed.
- **`payload`**: An object (`Record<string, unknown>`) containing any data passed to the task.
- **`context`**: A `TaskContext` object (may include `waitUntil` depending on the runtime).

```ts
interface TaskEvent {
  name: string;
  payload: TaskPayload;
  context: TaskContext;
}
```

### Registering tasks via config

In addition to file-based scanning, tasks can be registered directly in the Nitro config. This is useful for adding a description to a scanned task, or for tasks provided by modules and pointing to custom handler paths.

```ts [nitro.config.ts]
import { fileURLToPath } from "node:url";
import { defineConfig } from "nitro";

export default defineConfig({
  serverDir: "./server",
  experimental: {
    tasks: true
  },
  tasks: {
    // Describe a task scanned from `server/tasks/db/migrate.ts`
    "db:migrate": {
      description: "Run database migrations"
    },
    // Register a task from a custom location
    "db:seed": {
      handler: fileURLToPath(new URL("scripts/seed.ts", import.meta.url)),
      description: "Seed the database"
    }
  }
})
```

::warning
Unlike route handlers, a task `handler` is imported as-is and is **not** resolved against the project root, so a path such as `"./scripts/seed.ts"` will fail to resolve at build time. Use an absolute path (for example via `fileURLToPath(new URL(..., import.meta.url))`) or a package name.
::

If a task is both scanned from the `tasks/` directory and defined in the config, the config-defined `handler` takes precedence.

## Scheduled tasks

You can define scheduled tasks using Nitro configuration to automatically run at the specified cron-formatted times.

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  scheduledTasks: {
    // Run `cms:update` task every minute
    '* * * * *': ['cms:update'],
    // Run a single task (string shorthand)
    '0 * * * *': 'db:cleanup'
  }
})
```

The `scheduledTasks` config maps cron expressions to either a single task name (string) or an array of task names. When multiple tasks are assigned to the same cron expression, they run in parallel.

::tip
You can use [crontab.guru](https://crontab.guru/) to easily generate and understand cron tab patterns.
::

When a scheduled task runs, it automatically receives a `payload` with `scheduledTime` set to the current timestamp (`Date.now()`).

::note
Prefer `scheduledTasks` when your deployment target supports it (see [platform support](#platform-support)). Nitro wires up the platform's native scheduler for you. If your platform is not supported, you can still trigger tasks from an external scheduler by calling [`runTask`](#programmatically-run-tasks) from an authenticated HTTP endpoint.
::

### Platform support

- **`dev`**, **`node_server`**, **`node_cluster`**, **`node_middleware`**, **`bun`** and **`deno_server`** presets are supported by the [croner](https://croner.56k.guru/) engine. Schedules stop when the Nitro `close` hook runs. With `node_middleware`, Nitro does not own the server, so call `useNitroHooks().callHook("close")` when your host server shuts down.
- **`cloudflare_module`** and **`cloudflare_pages`** presets have native integration with [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/). Nitro automatically generates the cron triggers in the wrangler config at build time - no manual wrangler setup required.
- **`vercel`** preset has native integration with [Vercel Cron Jobs](https://vercel.com/docs/cron-jobs). Nitro automatically generates the cron job configuration at build time - no manual `vercel.json` setup required. You can secure cron endpoints by setting the `CRON_SECRET` environment variable.
- More presets (with native primitives support) are planned to be supported!

## `waitUntil`

When running background tasks, you might want to make sure the server or worker waits until the task is done.

An optional `context.waitUntil` function _might_ be available depending on the runtime.

```ts
import { defineTask } from "nitro/task";

export default defineTask({
  run({ context }) {
    const promise = fetch(...)
    context.waitUntil?.(promise);
    await promise;
    return { result: "Success" };
  },
});
```

## Programmatically run tasks

To manually run tasks, you can use the `runTask(name, { payload?, context? })` function from `nitro/task`.

**Example:**

```ts [server/api/migrate.ts]
import { defineHandler } from "nitro";
import { runTask } from "nitro/task";

export default defineHandler(async (event) => {
  // IMPORTANT: Authenticate user and validate payload!
  const payload = Object.fromEntries(event.url.searchParams);
  const { result } = await runTask("db:migrate", { payload });

  return { result };
});
```

### Error handling

`runTask` throws an HTTP error if:

- The task does not exist (status `404`).
- The task has no handler implementation (status `501`).

Any errors thrown inside the task's `run` function will propagate to the caller.

## Run tasks with dev server

Nitro's built-in dev server exposes tasks to be easily executed without programmatic usage.

### Using API routes

#### `/_nitro/tasks`

This endpoint returns a list of available task names and their meta.

```json
// [GET] /_nitro/tasks
{
  "tasks": {
    "db:migrate": {
      "description": "Run database migrations"
    },
     "cms:update": {
      "description": "Update CMS content"
    }
  },
  "scheduledTasks": [
    {
      "cron": "* * * * *",
      "tasks": [
        "cms:update"
      ]
    }
  ]
}
```

#### `/_nitro/tasks/:name`

This endpoint executes a task. You can provide a payload using both query parameters and body JSON payload. The payload sent in the JSON body payload must be under the `"payload"` property.

::code-group
```ts [server/tasks/echo/payload.ts]
import { defineTask } from "nitro/task";

export default defineTask({
  meta: {
    name: "echo:payload",
    description: "Returns the provided payload",
  },
  run({ payload, context }) {
    console.log("Running echo task...");
    return { result: payload };
  },
});
```
```json [GET]
// [GET] /_nitro/tasks/echo:payload?field=value&array=1&array=2
{
  "field": "value",
  "array": ["1", "2"]
}
```
```json [POST]
/**
 * [POST] /_nitro/tasks/echo:payload?field=value
 * body: {
 *   "payload": {
 *     "answer": 42,
 *     "nested": {
 *       "value": true
 *     }
 *   }
 * }
 */
{
  "field": "value",
  "answer": 42,
  "nested": {
    "value": true
  }
}
```
::

::note
Keys specified in the JSON body overwrite any values present in the query parameters.
::

### Using the CLI

::important
It is only possible to run these commands while the **dev server is running**. You should run them in a second terminal.
::

#### List tasks

```sh
nitro task list
```

#### Run a task

```sh
nitro task run db:migrate --payload "{}"
```

The `--payload` flag accepts a JSON string that will be parsed and passed to the task. If the value is not a valid JSON object, the task runs without a payload.

::read-more{to="/docs/cli#nitro-task"}
See the CLI reference for all `nitro task` subcommands and flags.
::

## Notes

### Production task CLI

Node server (`node` / `node-server`), `node-middleware` and `node-cluster` builds can
opt into a separate task executable:

```ts [nitro.config.ts]
export default defineConfig({
  serverDir: "./server",
  experimental: { tasks: true, taskCLI: true },
  tasks: { "db:migrate": { description: "Migrate the database" } },
});
```

```sh
node .output/tasks/index.mjs --help
node .output/tasks/index.mjs list
node .output/tasks/index.mjs run db:migrate --payload '{"force":false}'
```

The executable is recorded in `nitro.json.taskEntry`, relative to the output
directory. Copy the **complete output** to the destination; it needs neither the
project sources nor a running development server. The output's `tasks/` directory
is reserved when this option is enabled. Development builds do not emit it.

`list` writes a JSON array with each task's name, configuration description and
`implemented` flag. Only build-time configuration is listed: descriptions exported
from a handler cannot be discovered without loading that handler. Help, list and
invalid commands do not initialize the app or evaluate user plugins or handlers.
Payloads must be JSON objects; arrays, null, unknown options and duplicate payload
options are rejected before initialization.
Task names owned by `Object.prototype`, such as `constructor` and `toString`,
are reserved by the current task runtime and cannot be run through this CLI.

`run` initializes the app, awaits asynchronous plugins, calls the existing
`runTask`, writes its return value as JSON, and awaits the app's registered close
hooks once. Runtime configuration and its environment overrides work as in the
server. User code may write additional logs. Exit codes are 0 for success, 2 for
usage errors and 1 for initialization, task, serialization or cleanup failures.
A cleanup failure is reported separately and does not replace an earlier error.

SIGINT and SIGTERM interrupt waiting initialization or execution, attempt the
already registered cleanup and exit with 130 or 143 unless a failure was
already observed. A second signal forces exit if cleanup does not settle. This
does not add an abort signal to `TaskContext` or make arbitrary synchronous user
code interruptible. On interrupted initialization, hooks registered later cannot
be awaited. Normal output and error diagnostics are flushed before exit; a signal
during output can interrupt it so cleanup and exit can proceed.

The task executable does not start Nitro's HTTP listener, scheduler or cluster
pool. Running a task still loads the app's plugins and may evaluate non-lazy user
route modules; user code can have its own side effects. Tasks retain the same
process-local execution semantics as `runTask`; separate CLI processes do not
provide a distributed lock or queue.

The executable is built separately with dynamic chunks, even when the main server
uses `inlineDynamicImports`. Help and list never load handlers; run resolves the
selected task lazily, while shared dependencies and app/plugin modules can also
be evaluated. The main entry, output naming and cluster worker contract are
unchanged. Bundler transforms run for the separate graph, without replaying the
Nitro project build lifecycle. Both builds use the same resolved environment.
This option requires a bundled Node production
preset and is experimental. Plugins that replace Nitro's internal plugin objects
or change the reserved task entry or output contract are rejected.

Output plugins, code addons (such as `banner`) and supported code-generation and
sourcemap settings are applied to the task executable too. Output plugins keep
their output-only hooks. The executable controls its own destination, filenames,
format and chunk layout, including sourcemap filenames. Multiple output
configurations, non-empty `output.paths`, customized options for other module
formats and unknown output options are rejected rather than silently omitted.
Move required transformations to supported output plugins or disable `taskCLI`
for incompatible configurations.

### Concurrency

Task runs are deduplicated by **task name**: each task can have at most one running instance per server instance. Calling `runTask` for a task that is already running does not start a new run: all concurrent callers, even those passing different payloads, share the result of the first in-flight run.

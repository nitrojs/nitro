> Nitro reports where each request spends its time with the `Server-Timing` response header.

The [`Server-Timing`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing) header carries backend metrics to the client. Browsers show them in the devtools **Network** panel (under the **Timing** tab of a request) and expose them to JavaScript as [`PerformanceServerTiming`](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceServerTiming) entries.

In development, Nitro adds this header to every response, with metrics for its built-in KV storage, database and cache layers. In production, it is [opt-in](#enabling-it-in-production).

```http
Server-Timing: kv;desc="3 ops";dur=1.2, db;desc="2 queries";dur=4.1, cache;desc="hit";dur=0.4, total;dur=12.3
```

The header covers every request handled by Nitro, including filesystem routes, the [server entry](/docs/server-entry) and the [renderer](/docs/renderer).

## Metrics

| Metric | Description |
| ------ | ----------- |
| `total` | Time spent inside Nitro until the response headers are ready. For streamed responses, it does not include the time spent streaming the body. |
| `kv` | Time spent waiting on [KV storage](/docs/storage) operations made with `useKV()`. The description holds the number of operations. |
| `db` | Time spent waiting on [database](/docs/database) queries made with `useDatabase()`. The description holds the number of queries. Requires `experimental.database`. |
| `cache` | Time spent in [cached handlers](/docs/cache#cached-handlers), including cache route rules. The description holds the cache status: `hit`, `miss`, `stale`, `revalidated` or `bypass` (the request skipped the cache, e.g. with `shouldBypassCache`). |

A metric is only included when the request used it. Descriptions never contain storage keys, SQL queries or driver names.

### How durations are measured

Each `dur` is the wall-clock time during which at least one operation of that kind was in progress. Parallel operations count once:

```ts [routes/profile.ts]
import { defineHandler } from "nitro";
import { useDatabase } from "nitro/database";

export default defineHandler(async () => {
  const db = useDatabase();
  // Two 50ms queries in parallel: db;desc="2 queries";dur=50
  const [user, posts] = await Promise.all([
    db.sql`SELECT * FROM users WHERE id = 1`,
    db.sql`SELECT * FROM posts WHERE author = 1`,
  ]);
  return { user: user.rows?.[0], posts: posts.rows };
});
```

The same two queries run one after the other report `dur=100`. As a result, `kv`, `db` and `cache` durations never exceed `total`, and you can read them as "how long this request waited on X".

::note
Metrics can overlap. A cached handler that misses includes the time spent running the handler, and with the [`kv` cache driver](/docs/cache#kv-storage), cache reads and writes also count as `kv` operations.
::

## Runtime support

`total` and `cache` work on every runtime.

`kv` and `db` need the `node:async_hooks` and `node:diagnostics_channel` modules to attribute operations to the current request. They are available on Node.js, Bun, Deno and Cloudflare Workers (with `nodejs_compat`). On other runtimes, these metrics are left out.

## Adding your own metrics

Nitro does not need its own API for custom metrics: entries you add with your framework are merged with Nitro's.

In Nitro routes, use the `setServerTiming()` and `withServerTiming()` utilities from H3:

```ts [routes/report.ts]
import { defineHandler } from "nitro";
import { setServerTiming, withServerTiming } from "nitro/h3";

export default defineHandler(async (event) => {
  const data = await withServerTiming(event, "fetch", () => fetchReport());
  setServerTiming(event, "render", { dur: 3.2, desc: "Render" });
  return data;
});
```

In a [server entry](/docs/server-entry) built with another framework, use its own tools, such as [`hono/timing`](https://hono.dev/docs/middleware/builtin/timing) or [`@elysiajs/server-timing`](https://elysiajs.com/plugins/server-timing), or set the header on the response yourself:

```ts [server.ts]
export default {
  async fetch(req: Request) {
    const start = performance.now();
    const body = await render(req);
    return new Response(body, {
      headers: { "server-timing": `render;dur=${performance.now() - start}` },
    });
  },
};
```

Nitro keeps these entries and appends its own after them:

```http
Server-Timing: render;dur=8.4, total;dur=9.1
```

## Cross-origin requests

Browsers only expose `Server-Timing` metrics to scripts from the same origin. To make them visible to other origins, add a [`Timing-Allow-Origin`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Timing-Allow-Origin) header with a route rule:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  routeRules: {
    "/api/**": { headers: { "timing-allow-origin": "https://example.com" } },
  },
});
```

## Enabling it in production

Server timing is enabled by default in development only. To also send the header from production builds, enable the [`serverTiming`](/config#servertiming) option:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  serverTiming: true,
});
```

::warning
The header is visible to every client. The metrics are generic and never include keys or queries, but they still reveal how long requests spend on storage, the database and the cache.
::

::note
Server timing adds a small cost to every request: `kv` and `db` track each request in an async context (Nitro reuses its own when [`experimental.asyncContext`](/config#asynccontext) is enabled), and h3 copies returned responses to add the header.
::

To choose which metrics are reported, pass an object instead. Only the metrics set to `true` are enabled, in both development and production:

```ts [nitro.config.ts]
import { defineConfig } from "nitro";

export default defineConfig({
  serverTiming: {
    total: true,
    cache: true,
  },
});
```

To disable the header in development too, set `serverTiming: false`.
